Start every task by identifying the intended paths and running route_task or the Python CLI route command in README.md. Treat new subsystems, public contract changes, policy changes and ambiguous scope as FULL. A user may always request a higher profile. Recheck the actual diff against the starting revision before reporting completion. Include verification failures in your report.

FAST uses a direct edit and a reviewed Git diff. STANDARD uses focused Trail evidence, Tach and pytest. FULL needs reviewed intent, a compiled contract, an isolated attempt, explicit approval for material architecture changes, passing requirement-linked evidence, and final intent review. Stop for a revised contract when scope expands. Allow at most two repair attempts per contract. Decision models advise rather than enforce: the assess command floors on the routing rules and observed interface impact, consults a provider only inside the ambiguous STANDARD band, never lowers the floor, and records every decision under .harness.

Run the harness from the project root. Both clients can use its CLI when MCP is unavailable. The Lines design bible is a reference for harness cases. Keep gameplay development separate.

Use the shared CLI or MCP from any client. Use scripts/roles.py for automated delegation when a native adapter is installed. Keep the client selected by its project launcher. When launching directly, pass --client with the native adapter name. Codex assigns architect and reviewer to Astra and engineering to Sol. OpenCode uses the corresponding harness agents and provider-qualified models in opencode.json. Start a fresh invocation per task with its request and relevant evidence. A process already launched in its assigned role should do that task directly. Keep routine FAST edits on the direct path.

External communication: do not post, comment, file or publish on public services (GitHub issues or pull requests, forums, chats) on the user's behalf without explicit advance approval for that specific action. The user does not generally post on GitHub: prepare filing materials and let the user file manually by default. A target repository must specifically welcome agent-filed contributions, per its contributing or issue policy, before an agent filing is even proposed. A local credential authorizes reading, not public speech. Approvals must be unambiguous: name the destination service, the target repository and the account that will be publicly seen, in plain words rather than tool jargon, so a tired reader can parse exactly what is being approved. After approval, show the final content and destination once more before sending, and record the approval with the filed material under .harness/filings/.

Development order: finish the design before field-testing it. Reach a stable version whose designed features all make sense and pass their checks — the point where further improvement costs more than it returns — before running the harness on real work. A field trial is expected to generate its own failure list, which is evidence for the next cycle rather than a reason to reopen design mid-trial. Benchmarks and comparisons wait for that point; do not propose them early.

Fundamentals first: the harness core stays language-neutral. Language tooling (Godot now, other targets later) enters as pluggable adapters, never as core structure. If the fundamentals are right, a language's specifics should be minor; if they are not, fixing language nuances will not help. Do not shape core design decisions around one language.

Naming: this repository's harness is called Archforge. The bare word harness means an agent harness — OpenCode, Codex, Claude Code and the like — since those are what run Archforge's CLI and MCP server. Use Archforge in speech, tickets, documents and reports for the compiler, contract and verification workflow defined here, so the two never blur.
